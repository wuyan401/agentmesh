# M5 独立验证：打回与换人（未央亲手跑，不采信 DSH 自述）

DSH 的 M5 交付里，8 张演练卡的 `rejection_count` 全是 0 —— 它验了分工、SoD、整合、协作史，
但**没有端到端跑过「卡被打回两次 → 排除经手者 → 换第三方」**。这一环我自己补。

## 环境

`D:\AI\workspace\_m5proj`，三个 agent，画像各不相同，全部 `manual_locked=true`：

| agent | 质量分 | 花费 | 可靠性 | 定位 |
|---|---|---|---|---|
| dsh-01 | 84 | 2 | 90 | 架构 / 契约 / 重构 |
| dsh-02 | 72 | 1 | 78 | 前端 / 单文件 / 快 |
| hermes-01 | 88 | 3 | 85 | 审查 / 文档 / 边界 |

## 逐步记录（全部是命令回读，不是推测）

**1. 评分选人成立**

建卡 `T-000001`（backend_dev，scope `src/sum.js`）后派发：

```
→ T-000001 dsh-02 (backend_dev, pid 22636)
```

按公式算：dsh-02 = 0.55×0.72 + 0.20×1.0 + 0.15×0.78 = **0.713**；
dsh-01 = 0.55×0.84 + 0.20×0.5 + 0.15×0.90 = **0.697**。
便宜的 dsh-02 以 0.016 之差赢过质量更高的 dsh-01 —— 说明 cost 维度真的进公式了。

**2. 第一次打回**

关掉 `auto_review` / `auto_integrate` 后手工裁决：

```
✔ T-000001 rejected by mesh-human/S-000003 (R-0001)
   status=rejected  rej=1  rejected_by=['dsh-02']  impl=dsh-02
```

**3. 重新派发换了人（评分驱动的连带效果）**

```
→ T-000001 dsh-01 (backend_dev, pid 20572)
```

阈值是 2，这次才 1 次打回却换了人。原因不是阈值 —— 是**打分变了**：
打回让 dsh-02 的可靠性从 78 掉到 **0**（成功率 0%），总分掉到 0.596，
于是 dsh-01 的 0.697 反超。评分驱动的换人比硬阈值更贴近「派给评分更强的 agent」。

**4. 第二次打回**

```
✔ T-000001 rejected by mesh-human/S-000003 (R-0002)
   rej=2  rejected_by=['dsh-02','dsh-01']
```

`rejected_by` 记的是**所有**经手者，不只是最后一个。

**5. 第三次派发：两个实现者都被排除**

```
→ T-000001 hermes-01 (backend_dev, pid 39420)
```

dsh-02 和 dsh-01 都没被选中，卡交给了从未碰过它的 hermes-01。

## 结论

用户要求的「验收不通过打回重改、多次打回派给另一个评分更强的 agent」**端到端成立**，
而且是由真实调度器 + 真实 worker 进程跑出来的，不是单元测试里的桩。

## 一个诚实的操作失误

第一次打回时我在理由里要求「新增 `test/sum.test.js`」，但那张卡的 `scope.write` 只有
`src/sum.js` —— 是我提了 scope 之外的要求，worker 按规矩不能写。第二次打回改成
scope 内的要求（`src/sum.js` 里加 `typeof` 校验）才公平。这不算平台缺陷，
但说明**审查者的意见也必须落在 scope 内**，否则返工无从满足。
